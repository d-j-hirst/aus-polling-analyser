# C++ live turnout count calculation

This document explains how to reproduce and inspect the C++ calculation of votes remaining during a live count. It describes the input format, the comparison with Python, the optional use of estimated counts in the forecast and the diagnostic output produced alongside a LiveV2 run.

The calculation starts from a fixed set of possible pre-election vote counts and updates them using the current first-preference counts. When a matching input file is available, it runs in **counts mode**: it uses mean counts when preparing vote composition, then samples the distribution of remaining counts in forecast iterations. Those iterations include the possibility of no further votes and occasional substantial late batches. Optional **shadow mode** records estimates alongside the existing forecast without changing it. The exporter currently supports SA 2026 and Federal 2025.

## What the calculation uses

The **frozen prior** is the pre-election distribution: a set of possible final formal vote totals and category counts, generated by the Python turnout prior. An outcome contains counts for every district together, retaining relationships between districts. The C++ updater reads these outcomes rather than fitting historical parameters itself. Each update starts from this same account; it does not update the result of an earlier snapshot.

An input unit is an ordinary booth, an ordinary pre-poll voting centre (PPVC), or a declaration category such as Postal. Its metadata identifies its district, historical group, starting weight, reliable historical match, EAV service status and any known closure or calibration exclusion. The weights divide the historical groups; they do not provide evidence for historical category splits that were never reported.

Reported ordinary and PPVC booths are approximately complete. Declaration counts are lower bounds. Raw reported counts and counted FP votes remain unchanged, while estimated additions are allocated within a finite enrolment account using the same transformed calculations as Python. Separate preference rechecking, described below, can revise a scenario's counted TCP allocation without adding votes. EAV services receive their separate starting-size treatment. Conservative PPVC compensation and the explicitly configured delayed-return adjustment follow the Python replay rules. Experimental pooled size-change alternatives are not enabled by this contract.

Earlier cumulative declaration counts and whole historical-group totals supply evidence about whether counting has slowed. A historical group is a division supported by the earlier results: SA's early group includes PPVC booths and early declarations, whereas federal data supports separate categories. The artifact records each group's exact observed sum under `allocation:<group>`; Postal uses its existing category total. These measurements include ordinary and PPVC booths where they belong to the group, rather than trying to reconstruct their split from a combined ordinary-vote total.

The calculation uses the feed's timestamp, not the filename's capture time. Archived observations after the current source time are excluded, and the current LiveV2 counts replace any observation at that time. A missing measurement remains absent; it is not recorded as zero. Without earlier observations, there is no evidence from a counting pause. An explicitly supplied receipt timetable can still reduce routine expected additions after the processing allowance.

The exported declaration receipt cutoffs are midnight at the end of 16 May for Federal 2025 and 28 March at 6 pm for SA 2026. A cutoff means ballots should have arrived, rather than that every district has processed them. Other elections require their own explicit dates. The ECSA first-preference finalisation flag can close a district account. Declared winners and two-candidate completion are not used as first-preference finalisation flags.

## Why remaining allowances can recede

An aggregate allowance can assign too many votes to the small declaration categories still open after the larger booths have finished. The updater retains each declaration's own expected remainder before that allowance rescaled it. As counting in the whole group settles, it moves gradually towards the own-category estimate. It gives less influence to an estimate that would increase the allowance: a larger prior alone is weak evidence that more votes are still to arrive.

The progress response is `1 - exp(-(evidence / 0.5)^2)`. Within each prior outcome, a logistic response with scale 0.5 in the difference between the two log odds favours reductions smoothly. These scales are explicit assumptions from the offline comparison, rather than fitted completion probabilities. There are no completion cutoffs or hard vote ceilings. Joint transformed accounting allows a lower formal total while preserving counted votes, booth estimates and the enrolment bound. The category-specific late-batch mixture is applied afterwards, with its usual evidence and receipt-window treatment.

The allocation model is identified as `live-allocation-1`, with count contract `live-counts-6`. Older artifacts lack its required group history and must be re-exported; no historical refit is needed. The count-version change also makes older GUI builds reject the new artifact instead of silently using their previous allocation rule. The adopted shadow rule uses the existing category uncertainty. The optional extra spread for unsupported finer splits remains an offline sensitivity experiment.

When a historical group supports one actual declaration category, completed ordinary/PPVC booths provide additional, conservative support for releasing its allowance. Booths are weighted by their expected sizes; the category's counted fraction reduces this influence when much of its own expected count remains outstanding. Mixed historical groups retain the group-progress rule, because completed booths do not establish their finer declaration splits.

## Rechecking preferences on counted ballots

Preference rechecking allows a reported TCP allocation to be revised without
adding votes. It is independent of turnout and outstanding-vote uncertainty.
Raw feed counts and FP counts remain unchanged. A scenario can transfer existing
preferences between the reported finalists, preserving the booth preference
pool and the district pair total. The main simulator receives that scenario's
adjusted counted pair, so the correction remains possible even with no further
votes expected.

The comparison uses ordinary booths and PPVCs with exactly matching FP and TCP
totals, the district's reported pair, and possible preference gains. Unfinished
preferences, other services and exhausted OPV counts do not supply a measured
flow. The preference flow is a finalist's TCP minus their own FP, divided by FP
for all candidates outside the finalist pair. The regression relates its log
odds to that finalist's transformed primary share, the largest non-finalist
party's share of the preference pool, and PPVC status. These predictors have
different parent groups: they describe an association rather than interchangeable
shares. Every target booth is omitted from its regression. Robust weighting
limits unusual peers' influence, and the comparison scatter gives more weight
to booths of similar formal size. Sparse comparisons retain fitting uncertainty;
a booth with no comparable peer receives both reported-flow recheck components,
but no regression-directed correction.

The four possible outcomes distinguish uncertainty about a count from evidence
that its allocation is wrong:

1. The allocation remains exactly unchanged.
2. A routine small recheck is centred on the reported preference flow.
3. A larger background recheck is also centred on the reported flow. Its chance
   and count allowance grow smoothly with booth size and remain available even
   when the booth agrees with the regression. The chance of a recheck therefore
   does not itself imply that votes should move towards the regression.
4. A regression-directed correction moves towards the predicted flow. Its
   probability depends on booth size and discrepancy, and its conditional
   destination approaches the full prediction as discrepancy increases.

The discrepancy score is the absolute observed-minus-predicted preference log
odds divided by the allowance for peer variation, sampling and regression
uncertainty. It is not a calibrated probability that the count is wrong. All
three changing outcomes use Student-t distributions with five degrees of freedom
on the transformed preference share. Their centres specify medians rather than
exact mean counts; the bounded transform can produce a small difference between
the two. Corrections may overshoot or move away from a component's centre. A
quarter-vote equivalent permits behavioural zeros while the unchanged outcome
retains their exact reported value.

For reproducibility, let `R = formal votes / 1000`, `s` be the discrepancy score,
and `logistic(x) = 1 / (1 + exp(-x))`. The fixed shared parameters are:

| Quantity | Value |
|---|---|
| Directed-correction probability | `logistic(-7.809508178103534 + 3.20705363776961 * log(1 + s*s) + 0.520532187574425 * log(R) + log(1 - exp(-R)))` |
| Background chance, conditional on no directed correction | `logistic(log(0.10534213368051161 / (1 - 0.10534213368051161)) + 0.39602184615771785 * log(R))` |
| Routine chance, conditional on neither directed nor background rechecking | `0.5327639742322045` |
| Routine count-scale allowance | `exp(0.08737413053901756) * R^0.339131984114037` votes |
| Additional background count-scale allowance | `exp(2.329939422870341) * R^0.5629780364803446` votes |
| Conditional fraction of the transformed gap closed | `0.8093269894532144 + (1 - 0.8093269894532144) * s*s / (s*s + 2.25)` |
| Directed Student-t scale | `exp(-0.22719181582595513) * size-matched peer scatter` |

The background count-scale allowance is the routine allowance plus the additional
allowance in the table. Let `M` be the preference pool and
`p = (reported preference gain + 0.25) / (M + 0.5)` be its reported share after
the quarter-vote adjustment. Each count-scale allowance `A` becomes
`log(1 + A / (M*p*(1-p)))` on the log-odds scale.
These are Student-t scales, not standard deviations, interval widths or count
limits. The component probabilities are absolute weights after applying their
conditional chances. The remaining weight leaves the allocation unchanged.

The size term reduces the directed correction's odds for small booths, rather
than multiplying its probability by a value below one. Compelling evidence can
therefore overcome small size without a probability ceiling. All responses are
continuous; there are no eligibility thresholds in booth size or discrepancy.

The shared parameters were fitted offline to changes between the Federal 2025
20 May snapshot and the 31 May reference. Five groups of seats were used for
comparisons, with each test group's seats absent from its parameter training;
the installed values then use the complete calibration sample. Later counts
calibrated those values only: live regression inputs come entirely from the
current snapshot. This is evidence from one election rather than independent
validation across elections.

Preparation retains the four largest correction contributors per district as
explicit mixtures and combines the others into 1,024 cached aggregate outcomes.
Main iterations choose one aggregate outcome and draw the explicit components.
The largest corrections retain continuous tails beyond the preparation sample;
the smaller contributors' tails have the bank's finite resolution. This error
source is separate from the normal preparation for outstanding-voter composition.
For a classic pair the transfer changes TPP; for another pair it changes TCP and
does not invent an observed classic TPP.

The analysis JSON records `live_analysis.preference_rechecking`, with version
`live-preference-rechecking-2`, calibration identity, preparation time, exclusions,
and per-booth probabilities, relative discrepancy, conditional movement and
expected revision in candidate votes. `broad_probability` is the absolute
regression-directed probability; `background_probability` is the separate
reported-flow component. They are separate from `routine_probability` and
`unchanged_probability`, and the four weights sum to one. The three
`*_log_odds_scale` fields describe their Student-t scales. The diagnostic also
identifies the explicitly drawn contributors. Unrandomised node
counts still describe the reported allocation and its outstanding-vote estimate;
simulated forecast distributions include the separate rechecking draw. No
additional environment variables or replay artifacts are required.

To inspect the regression evidence and later revisions used by the calibration,
generate the booth audit from saved GUI analysis snapshots. Run from `analysis/`;
the final snapshot in the input series is the later comparison reference and is
excluded from the test dates. This command evaluates the contemporaneous booth
regressions, rather than fitting the four-component correction distribution:

```powershell
.\.venv-win\Scripts\python.exe -B -m scripts.diagnostics.preference_flow_outlier_audit --series ../live_runs/2025fed-turnout2 --output ../downloads/turnout/preference-flow-audit/audit.json
```

## Why late batches are retained separately

A single standard deviation would obscure the distinction between an almost finished count and a small probability of a substantial late batch. The updater therefore retains three components: the broad previous-expectation distribution, very small additions, and a wider late-batch distribution. Their weights change continuously with counting evidence.

There is also an explicit, shared outcome in which the entire district receives no further votes. Its probability grows smoothly with count-weighted slowing evidence and falls with the broad expected remainder, including unreported booths. A known postal receipt window discounts it. Probability for previous expectations and small additions is reduced to accommodate this shared outcome. Exceptional batches retain a separately calculated low probability. These are shared assumptions, not fitted probabilities of completion; counting can resume in a later snapshot.

The sample matrices describe the branch with additional votes. The result retains the no-addition probability separately, and reported means and intervals combine both branches. For example, a 60% probability of no further votes and a conditional expectation of 100 additional votes gives a mean of 40. Keeping this outcome explicitly avoids dependence on whether a small preparation sample happened to draw it. Authoritative finalisation makes no further votes certain.

Each prior preparation outcome supplies eight inexpensive count draws by default for diagnostic means and intervals. Both additional components are also evaluated deliberately, even when a mixed sample does not select the rare batch. The in-memory result retains each component's transformed location, available capacity and weight for every preparation outcome. Counts mode samples these component distributions directly during the main iterations, so a rare batch is available even if the short diagnostic sample did not select it.

The artifact also retains distinct prior count responses for turnout, formality, early-vote conversion, postal conversion and composition within historical groups. A response describes how category counts change with one uncertainty source. These are prior count responses, not current party-share sensitivities. Counts mode chooses a joint prior outcome for the entire election, retaining the relationships these sources created, rather than adding their responses again as independent errors. LiveV2's separately prepared party-composition errors remain separate from this count draw.

## How the receipt timetable changes expected and possible additions

The purpose of the timetable is to let routine expected additions recede without ruling out an exceptional late batch. A small possibility of a batch should not maintain a large routine vote allowance indefinitely.

After the receipt cutoff, the updater allows 48 counting hours for processing, then reduces the previous-expectation amount through a smooth 12-hour transition. Sundays contribute half as much counting time as other days. Recent local counting can extend the processing allowance by up to 24 hours and retain some routine size: a recent volume equal to 2% of counted category votes supplies half the extension, and 5% supplies half the continuing-activity influence. These are continuous responses, not completion thresholds. Removed expected votes become unused enrolment capacity rather than being assigned to another category.

Counting activity is measured using both a sensitive and a more conservative change-size treatment, with equal influence on their resulting probabilities. After the receipt cutoff, a late backlog retains its influence on its own district but gradually loses influence on other districts. Small positive late batches also supply some evidence that routine processing is ending; downward corrections and large batches provide less of that evidence. Missing observations supply no invented activity or quietness.

Each unfinished declaration category retains a starting exceptional-batch probability of 2%. After the processing allowance, its time-decay factor halves over approximately 9.7 counting days. The probability is also smoothly reduced if little probability remains outside the shared no-addition outcome. There is no permanent probability floor. The conditional batch size uses that category's own outstanding estimate plus 5% of its counted votes and a small count equivalent. It does not inherit a shortfall imposed by the overall district total. The transition from the earlier treatment is gradual.

The schedule is identified as `live-declaration-schedule-1`, and the progress calculation as `live-late-counts-4`. Timing, activity responses and transformed component locations are prepared once per snapshot. Main simulation iterations continue to draw from the cached distributions; they do not traverse count history or recalculate the timetable.

## Reproducing the input and comparisons

The installed model can be applied to an operator's own authorised feeds. Its historical live calibration cannot be reproduced by cloning this repository: live snapshots, no-results allocation exports and their close derivatives are private local inputs. Public final-result exports and statistical reports remain available for historical analysis.

The maintained turnout prior presets and aggregate new-PPVC size assumptions are in `analysis/lib/turnout/live_parameters.json`. The replay loader and C++ exporter use those parameters directly rather than accepting coefficients from an experimental result file. `LivePreferenceCorrections.cpp` maintains preference-rechecking coefficients directly; `analysis/lib/turnout/live.py` and `ppvc_sizes.py` maintain compensation and delayed-reporting settings, with their C++ counterparts in `TurnoutModel.cpp`. Private experiments can inform a deliberate parameter update but cannot automatically change installed tuning.

Parameter presets identify the category definitions and early/postal information used by each calibration. Applying a preset to another election still requires compatible category mappings, enrolment, previous-election sizes and that election's available early/postal counts. An election-specific frozen prior contains those inputs and sampled outcomes; it is a private generated artifact, not another set of fitted parameters.

Python commands default to the ignored `downloads/turnout/feed-archive/` directory. Set `POLLING_ANALYSER_FEED_ARCHIVE` once to use an external historical archive. If incoming snapshots are elsewhere, set `POLLING_ANALYSER_FEED_DOWNLOADS`; otherwise they use the same directory. Explicit `--archive`, `--downloads` and `--sources` options take precedence for individual commands. These settings are shared across elections.

Run the exporter from `analysis/` after preparing the private prior fixture, no-results allocations and authorised source archives:

```powershell
.\.venv-win\Scripts\python.exe -B -m scripts.turnout.turnout_cpp_fixture
```

Use `--election 2026sa` or `--election 2025fed` to export one election. `--archive` and `--downloads` select the source directories. The exporter performs no historical fitting. Its default is 256 preparation outcomes with eight count draws per outcome.

Re-export after updating to `live-late-counts-4`, then rebuild the application before using that artifact. The loader rejects artifacts without the matching calculation identifiers. This export regenerates comparison outputs and operational settings without fitting historical models.

The ignored `downloads/turnout/cpp-shadow/` directory receives two files per election:

- `2026sa-shadow.json` or `2025fed-shadow.json`: frozen prior outcomes, static unit metadata, source history, version identifiers, source hashes and separate prior count responses.
- `2026sa-checkpoint.json` or `2025fed-checkpoint.json`: the latest retained complete-election input account, plus Python mean totals and unit estimates for a portable C++ comparison and timing check.

The exporter also places source-backed comparisons under ignored `downloads/turnout/source-backed-fixtures/`. They contain real counts and must remain private. The committed `tests/fixtures/turnout/synthetic-turnout-v1.json` instead uses wholly fictional districts, booths and counts, covering no results, ordinary/PPVC reporting, partial declarations and a quiet count after the receipt deadline. It is generated without reading any election feed:

```powershell
.\.venv-win\Scripts\python.exe -B -m scripts.turnout.turnout_synthetic_fixture
```

The portable `TurnoutModelTests` compares broad totals, category counts, unit additions, progress evidence, mixed outcomes and the parameters of both conditional late-count distributions. It also checks explicit finalisation and rejects incompatible versions, invalid counts and unsupported clocks. It runs through the existing portable test scripts. After building the portable tests, a complete-election checkpoint can be checked from the repository root with:

```powershell
.\cli-build\tests\TurnoutModelTests.exe . downloads\turnout\cpp-shadow\2026sa-shadow.json downloads\turnout\cpp-shadow\2026sa-checkpoint.json
.\cli-build\tests\TurnoutModelTests.exe . downloads\turnout\cpp-shadow\2025fed-shadow.json downloads\turnout\cpp-shadow\2025fed-checkpoint.json
```

Synthetic fixtures and private complete-election checkpoints use the same deterministic quantile grid in Python and C++. This separates differences in the calculation from differences between random generators. Ordinary Python replay scoring retains its existing generator. To compare an additional private small fixture, pass its path as the second argument to `TurnoutModelTests` after the repository root.

The turnout and preference-rechecking analysis commands are standalone. They are absent from the general pipeline registry and every generation profile, including **All required historical and active work**. Their artifacts have independent source fingerprints and model identifiers; they do not currently receive the general pipeline's dependency/freshness tracking.

## Automatic election selection and optional overrides

Normal GUI runs require no turnout environment variables. Each live simulation selects `downloads/turnout/cpp-shadow/<election>-shadow.json` relative to its project workspace, using the simulation's election code. For example, Federal 2025 selects `2025fed-shadow.json`, and SA 2026 selects `2026sa-shadow.json`. The selection is repeated for every live election, so switching projects within the application does not retain the previous election's prior.

An available file enables counts mode. If no automatic file exists, the application logs the expected path and keeps its existing live vote-size rules. An available but invalid or incompatible file still produces an error; automatic selection does not bypass the count and identity checks. Rebuild and restart after source changes. No variable changes or application restarts are needed merely to switch elections.

For a comparison using the automatically selected file, set one optional mode before starting the application:

```powershell
$env:POLLING_ANALYSER_TURNOUT_MODE = 'shadow'
```

Set the mode to `off` for the existing forecast without turnout diagnostics, or remove the mode override to restore automatic counts mode. Overrides are read from the process environment; changing an override requires restarting the application. In Visual Studio, use **Debugging > Environment** for the configuration selected beside the Run button.

An explicit custom file remains available for experiments:

```powershell
$env:POLLING_ANALYSER_TURNOUT_SHADOW = (Resolve-Path downloads\turnout\cpp-shadow\2026sa-shadow.json).Path
```

This file override is required to exist and match the election. Remove it, or set it to `auto`, to restore election-based selection. A retained explicit path takes precedence over automatic selection. LiveV2 matches units by district, name and role, attaches its mapped first-preference counts and prepares the count account once. Scenario copies share that immutable result instead of repeating the count preparation or copying all outcomes. A missing expected unit, changed role, new counted unit, conflicting enrolment or invalid artifact stops the enabled run with an explanation; it does not silently discard votes. Diagnostics record the selected path and whether selection was automatic.

The existing `.analysis.json` diagnostic export gains an optional `turnout_shadow` entry. It contains district totals and central 95% count intervals, the probability of no further votes, counted and expected category totals, unit estimates, PPVC compensation shifts, slowing evidence, component probabilities and conditional means, source identity, provenance and elapsed time. The `declaration_schedule` record identifies the timetable settings, elapsed counting hours, transition and exceptional-probability decay. Each late component records its `usual_size_factor`, the multiplier applied to routine remaining-count odds.

**Mean remaining** is mean estimated final formal votes minus currently counted formal votes. A conditional batch mean answers what that category could add if the batch component applied while other counts were held fixed; it is not the ordinary expected addition. Component probabilities include the shared no-addition event and sum to one for each category.

District totals and historical category groups also record count percentiles at the website's colour breakpoints: 0.1, 1, 5, 25, 75, 95, 99 and 99.9, alongside the median and 97.5th percentile. The central 95% interval ends at 97.5%, leaving 2.5% above it; a 2% exceptional component can remain beyond that endpoint yet appear at 99/99.9%. These count diagnostics do not determine the website's candidate-share colours, which also depend on vote composition. The outermost percentiles are approximate at the short preparation sample size.

Each unit additionally reports its own expected remainder before balancing, the imposed remainder before release, and the remainder after release but before the late-batch mixture. These values explain whether the aggregate allowance inflated a small category and how much the new rule relaxed it. `allocation_group_evidence` is the whole-group slowing score, while `allocation_progress_weight` is its response before the per-outcome directional adjustment. `broad_mean_total` now describes the account after allocation release and before the late-batch mixture. The diagnostic includes the allocation-model identifier and both response scales.

The FP comparison preserves counted party votes and applies the existing LiveV2 remaining-vote composition to the changed remaining amount. If the existing projection supplies no additions, its overall projected composition is used. Unsupported compositions are identified rather than invented. The reported percentage-point changes illustrate count effects with composition held fixed; they are not a new forecast distribution or evidence that winner uncertainty is calibrated.

## Using mean counts in the forecast

Counts mode checks whether the estimated amounts and completion weights can be used consistently throughout the live forecast. It replaces ordinary, PPVC and declaration size expectations with their mean final formal counts from the turnout calculation. Both the baseline-composition comparison and the current projection use these same sizes. An election with no first-preference counts retains the existing baseline calculation exactly.

Counts mode is selected automatically when the election's artifact exists. An explicit `counts` mode override has the same behaviour. The current compatible artifacts can be reused; automatic selection does not require refitting or re-exporting them. Unknown modes are rejected explicitly.

During preparation, FP means and completion use the same fractional count target at every hierarchy level. The preference-count account also includes formal votes whose FP count has reported but whose preferences have not. For example, 100 counted FP votes, 97 counted TCP votes and 5.25 expected additional FP votes give targets of 105.25 for both FP and TCP. Three votes already exist in the FP account and need estimated preferences; only 5.25 votes are additional turnout. Both counted TCP candidates remain fixed, and TCP completion is 97 divided by 105.25. Accepted partial ordinary-booth pairs receive the same treatment as declaration batches.

When a simulation outcome includes no additional FP votes, estimates for those three missing preferences remain, with uncertainty in their allocation. The category cache includes them in its base account, separately from the sampled future FP additions; only reported candidate counts impose fixed lower bounds. A completely unreported pair is estimated from the entire FP target. If published TCP exceeds FP, its candidate counts and excess are preserved rather than reduced to force agreement. This compulsory-preferential approximation does not implement OPV exhaustion: an OPV prediction needs an explicit estimate of votes continuing to the final pair. Minor count-stage differences and corrections to already-reported preferences are separate from missing preference counts. FP-derived TPP estimates use the FP target continuously, including above 99% completion. Explicitly unavailable services retain zero weight.

The existing reduced preparation still estimates uncertainty in the composition and preference flows of outstanding votes. In counts mode its legacy declaration-size draw is disabled, since it would overlap with the new count distribution. The conversion uses the local relationship between a remaining-vote share and a full-seat share; it is an approximation, not a separately calibrated uncertainty model. FP changes retain the effect of normalising separate party estimates together, while TCP/TPP changes move a single final-pair share. Possible zero allocations use a quarter-vote equivalent when transformed. Observed classic TPP counts constrain TPP variation; inferred TPP votes from FP are not recorded as measured TPP counts.

For a main iteration, counts mode chooses one prior outcome shared across seats, then samples each seat's no-addition event and each unfinished declaration's conditional component. Categories are allocated jointly within the available enrolment account. Cached category mixes turn these sampled additions into FP/TCP/TPP projections without repeating booth calculations. Preparation's composition variation changes the mix of remaining voters; a larger sampled batch therefore has a larger absolute effect. Completion and confidence use the sampled count before the forecast consumes it. A no-addition outcome removes further FP votes, but retains uncertainty in preferences on FP votes whose pair count is still unreported.

The main simulator groups each feed candidate exactly once, either as a represented party/candidate or within Others. A small represented independent remains separate; a combined Coalition share represents both Liberal and National votes. After prior blending and normalisation, the simulator reallocates only the remaining vote pool on the transformed scale. Published candidate counts stay fixed. A later Liberal/National split preserves each party's individual count. TCP count constraints apply when the simulated finalists match the measured pair; a different pair still requires preference estimation.

The diagnostic retains the shadow account and mechanical FP comparison, labelled `mode: counts`. Its `forecast_integration` entry identifies `live-count-integration-3`, whether means were requested and activated, whether count uncertainty is installed, maximum FP accounting error and the smallest projected-minus-counted party count. `integrated_projections` records each seat's prepared mean FP/TCP/TPP totals and completion/confidence values; it is not an export of every stochastic iteration. Its `fp_without_reported_tcp` field sums positive FP–TCP differences across the seat's checked booth records, while `tcp_above_reported_fp` sums differences in the opposite direction. Measuring them separately prevents one booth's excess from hiding another booth's missing preferences. Missing allocations for any current booth, including an unreported booth, stop counts mode rather than silently retaining a legacy size outside the model's account. Count drawing and composition reweighting use immutable shared inputs and deterministic iteration keys.

## Checking the implementation and interpreting its limits

The portable regression asks whether Python and C++ apply the same count rules
and preserve the same accounting. Its five synthetic scenarios compare broad
and final totals, category allocations, unit additions, slowing evidence and
conditional late-batch components. Separate account checks cover fractional
remaining counts, unfinished preferences, candidate-count preservation and
explicit no-addition outcomes. Automatic artifact selection is tested using
fictional inputs under two different election identifiers.

These are implementation checks, not evidence that synthetic elections reproduce
real voter behaviour. Historical accuracy, preference-correction calibration
and full GUI runtime require an operator's private feed archive. The optional
local fixture and full-election checkpoint commands above retain those checks
without distributing the input counts. Live analysis remains outside the main
forecast pipeline's profiles and generated-data archive.

Re-export a local artifact after changing its source evidence, installed prior
parameters or sampling code. The export records hashes and calculation versions;
C++ checks compatible versions and count accounting, but does not recompute the
recorded source/code hashes. The stored hashes provide traceability rather than
the general pipeline's automatic freshness enforcement.
